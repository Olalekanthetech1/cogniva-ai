# Cogniva

**Understand More. Think Better.**

Cogniva is a global, AI-powered learning companion designed to help students build understanding through guided reasoning, interactive explanations, and evidence-aware learning support. Institution and academic context are optional personalisation, not prerequisites for learning.

## Product principles

- **Teach, don't merely answer.** Guide students through a problem one meaningful step at a time.
- **Preserve student agency.** Ask for attempts, offer progressive hints, and explain the current step without silently advancing.
- **Be honest about uncertainty.** Confirm ambiguous image/document extraction and disclose unavailable or failed verification.
- **Make AI limitations visible.** Cogniva is AI-powered and can make mistakes in explanations, calculations, and feedback; learners should verify important answers.
- **Ground academic claims.** Use uploaded learning materials and credible sources where appropriate; never invent citations.
- **Verify where possible.** Use deterministic tools and subject-specific checks when a capability is available.
- **ZeroMock.** No fabricated production data, pretend processing, static AI answer fallbacks, or false verification statuses.
- **Build incrementally.** Keep the architecture modular without creating premature microservices.

## Repository layout

The intended monorepo structure is documented in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). The initial application lives in `apps/web`; reusable domain capabilities live in `packages/`; background workloads, tests, and product documentation remain separate.

## Product scope

Cogniva is intended for undergraduate university students across academic disciplines. The first connected learning journeys are text-first Socratic tutoring and topic-based personal learning plans. Learners can review generated concept relationships and approve a personal plan. Approved plan units and standalone sessions use CTL v1.2 adaptive response modes: linked-unit lessons, concept mini-lessons, structured problem-solving openings with adaptive follow-up, attempt feedback, and focused assistance for hints, simplifications, examples, and recaps. Clear new tasks can switch a standalone session's teaching mode. Mode contracts are instructional guardrails; lesson content is generated by the configured provider. No persisted hint stage, mastery, or completion claim is made. Editing the outline and full Home/Learn integration are still being built. Subject breadth will expand through capability-declared subject modules rather than unsupported claims that every subject is fully verified.

## Engineering status

The web application, PostgreSQL/Drizzle data layer, and Better Auth integration are implemented. The text-first tutor has authenticated, persisted session APIs and provider-backed responses when the Socratic task route and matching server credential are configured. Tutor replies from all supported providers use one safe Markdown/KaTeX renderer; common TeX delimiters, legacy square-bracketed formulas, and clearly mathematical expressions after numbered rule labels are normalized for display without changing saved response text. Explicit attempts are persisted, and a bounded deterministic arithmetic verifier supports only its documented numeric forms. The personal-learning-plan schema already exists; the current implementation adds authenticated topic-plan generation and owner-scoped plan retrieval using the configured learning-plan provider route. Provider output is strictly validated before revision data is committed. Learner relationship decisions and plan approval are available. Approved learning-plan units can launch Tutor sessions linked to the revision and unit. Linked sessions retain the CTL structured lesson opening and adaptive continuation. Standalone concept/topic starts use a validated concept mini-lesson; problem sessions use a structured walkthrough covering the governing principle, strategy, worked reasoning, verification, and transfer; attempts and clarifications receive turn-specific feedback. CTL response modes are instructional policies, not persisted lesson stages. Persisted lesson-stage transitions and explicit stage controls are not implemented. Editing plan content remains unfinished. Home now surfaces genuine active Tutor sessions and learner-approved personal learning plans from owner-scoped records; it omits Continue learning when no resumable sessions exist and reports activity retrieval failures without sample content. Progress remains unavailable because an evidence-backed progress model is not implemented. No provider benchmark has been completed and no universal model winner is selected. Phase 1.3a adds an administrator-managed multi-model registry for Gemini, Groq and Mistral, provider-native model discovery, exact-model connection tests, capability evidence review, and disabled-by-default task candidate assignments. The strict read-only Neon audit [#44717853498](https://github.com/Olalekanthetech1/cogniva-ai/actions/runs/44717853498) confirms migration 0000–0010 (11/11), the registry and routing-settings tables, required columns, enum labels, constraints, and indexes. Phase 1.3b adds a shared adaptive routing runtime for Tutor and learning-plan generation plus persisted administrator-controlled rollout settings. The additive migration 0010 introduces `ai_task_routing_settings` and seeds both tasks as `pinned`; migration 0010 was applied by [production migration run #44717431481](https://github.com/Olalekanthetech1/cogniva-ai/actions/runs/44717431481), verified by strict read-only audit #44717853498, and the application revision was deployed to Render as commit `44b4ec7f52f80249f44fd4daa90620742d6851b2`. Administrators can enable adaptive mode per task only when at least one model currently passes exact-model test, capability-evidence, task-assignment, credential, context and output-budget checks. Every learner request is checked again against its actual prompt. `AI_ROUTING_FORCE_PINNED=true` remains an emergency server-side rollback switch. Selection uses administrator priority and exact-model connection-test latency as a tie-breaker; it does not infer price or teaching quality. A selected provider failure is surfaced without silent model switching. No provider benchmark has been completed and no universal model winner is selected. Production deployment does not mean adaptive routing is active: both task modes remain `pinned` until eligible model candidates have been inspected and an administrator explicitly enables a task. Phase 1.1a and 1.1b are merged to `main` as additive migrations 0007 and 0008, with isolated PostgreSQL integration coverage. Both migrations were applied to Neon production on 19 November 2026 ([migration run #44615863935](https://github.com/Olalekanthetech1/cogniva-ai/actions/runs/44615863935)) and verified by a subsequent read-only audit ([run #44610442501, attempt 2](https://github.com/Olalekanthetech1/cogniva-ai/actions/runs/44610442501)): all 9 expected migrations are applied, with no missing migration files or unexpected ledger entries; all 31 Phase 1.1 target tables and all nine legacy academic tables are present. The audit inspected schema metadata in a PostgreSQL read-only transaction and did not inspect learner rows. No catalogue seed data, live source adapters, or ingestion jobs are included. Multimodal/document processing, general subject verification, persisted lesson-stage transitions, mastery estimates, and adaptive recommendations are not implemented.

## Phase 1 database setup

1. Copy `.env.example` to `.env.local`.
2. Create a PostgreSQL database and set `DATABASE_URL`. For a provider with separate pooled and direct connection URLs, set `DATABASE_MIGRATION_URL` to the direct URL for migrations.
3. Set `BETTER_AUTH_URL` and generate a secret with at least 32 characters of high-entropy random data. Do not commit it.
4. Configure `RESEND_API_KEY` and `RESEND_FROM_EMAIL` using a verified sender. Cogniva keeps registration unavailable until email verification can actually be delivered.
5. Generate and review a migration, then apply it:

```bash
pnpm db:generate
pnpm db:migrate
```

Do not run migrations against production without reviewing the generated SQL and taking an appropriate backup. GitHub Actions runs auth/profile integration coverage against an isolated PostgreSQL service with the committed migrations; it does not use or mutate the production database.

## Health check

`GET /api/health` is an application liveness endpoint. It confirms that the web process is responding; it does not claim that the database, authentication email, or AI providers are healthy.
